# Architecture

Tauri 2 hosts the Windows desktop application and the Debian x64 port. Rust owns SQLite, providers and audio; TypeScript renders the panel and a transparent widget with inline text/image cells. Production embeds the frontend with no internal application HTTP server.

## Profiles and persistence

`sherka-core` uses a settings database and one database per UUID profile. Identity, revision checks and schema versions reject stale edits and incompatible databases. Imports validate bounded JSON and images, re-encode PNG and reject executable or external resources. Exports exclude history, memories and secrets.

Essential and topical memories use profile-local FTS5. Structured proposals are validated against revisions, epochs and quoted sources before a transaction. Corrections/forgetting exclude obsolete exchanges from future context while retaining archives. Automatic extraction requires review.

Explicit conversation clearing cancels the current generation and extraction, retires the audio input session, then deletes all messages, source quotations, summaries and unapproved/retired memories in that companion's database. Active approved facts survive unless the user selects the separate erase-facts option. The transaction advances the memory epoch and rebuilds FTS indexes; secure deletion, vacuum and WAL truncation remove old database pages. Individual fact deletion also removes the row from exports and excludes past exchanges from recall to avoid immediately relearning it. Copies previously exported or backed up are outside this operation.

Whole-command privacy requests are matched locally in seven languages, including `/clear`; quoted, negated, conditional and mixed requests do not trigger deletion. Typed commands work without a configured model or speech engine. Spoken acknowledgements are ephemeral and never enter dialogue history. Hermes bypasses this command handler. Its panel action clearly limits deletion to Sherka's local history, stops an owned active run and retires client session references; it does not delete data on the Hermes server.

The interface locale is a global settings preference. TypeScript and Rust tray labels share the same seven-language catalog; only authored UI text is translated before inserting dynamic values. Custom personality, dialogue, memories and provider identifiers remain opaque. Custom profile language is fixed at creation, and the conversation prompt follows it.

The original Sherka's UUID is registered in settings. Her built-in personality and instructions follow the interface locale from seven authored presets, preserving provider choices. Personalization detaches the preset; copies and imports are independent. Locale changes bypass voice cancellation unless they change the active built-in character's language. That case cancels the old generation and stops capture before continuing with the new prompt language.

## Sessions and audio

Capture and response belong to a profile and generation (a [three-way conversation](#three-way-conversation) shares one generation between two speakers and may prepare the second reply while the first is spoken). Switching, interruption and pause cancel obsolete work; late events cannot reactivate it. Voice commands release their gate while awaiting VoiceStudio, keeping settings and exit responsive. A separate pending token handles pre-session waits.

CPAL capture/output feeds Silero speech confirmation, VoiceStudio transcription, the selected provider's SSE stream and VoiceStudio TTS. LM Studio, OpenAI Chat Completions and Anthropic Messages normalize final text and usage into the same pipeline; reasoning events are excluded. Sonora provides echo processing in speaker mode. Text and speech buffers are independent. TTS prepares upcoming passages during playback; short verses are grouped. The first passage is short (25–110 characters, and may end at a clause comma but never a decimal comma) because synthesis time grows with length; the second passage is medium and later ones group up to 320 characters. Bounded PCM queues can transition in one output callback. Heard receipts follow completed playback. Cancellation clears queued work; a passage already playing fades out over 30 ms rather than stopping mid-waveform, and that tail never produces a heard receipt.

The end of a turn needs `silence_ms` of silence; only 60 ms of sustained speech restarts that countdown, so a breath or click after the last word does not delay the reply. Streaming ASR combines confirmed segment finals with partial/cumulative summaries and deduplicates overlaps. A small, conservative cleanup rejects whole non-speech markers and the specific subtitle-credit hallucination; ordinary short answers remain valid. If speech resumes while recognition is flushing, a run/tag-scoped PCM buffer prepends the interrupted capture to the new input. It is bounded to 90 seconds and cleared on gaps, pause, failure, completion or session changes, so stale text and audio cannot cross companions.

Companions serialize provider, full API base, model and budget preferences without keys. Windows Credential Manager owns provider/base-scoped credentials; only the panel can query key presence, replace a key or remove it. Remote requests use HTTPS except loopback, do not follow redirects and never forward provider credentials to VoiceStudio. Context discovery precedes local model retirement, and remote adapters never call local model load/unload endpoints.

Linux uses the same credential scope through the desktop Secret Service's `secret-tool`, sending secrets on stdin rather than command arguments. It reports a missing or locked service without falling back to plaintext. External source links use `xdg-open` without shell interpolation. VoiceStudio startup can use an explicitly configured Python runtime; the Linux updater offers manual downloads rather than Windows replacement helpers.

VoiceStudio synthesizes a passage before returning audio, so synthesis can exceed the available buffer. No token-level speech generation or zero-latency guarantee is claimed.

Transient input-buffer congestion is distinct from a disconnected device. A full callback queue rebuilds capture/echo state and discards stale frames without clearing playback. A full desktop event queue similarly resets input dispatch. Recovery drops any incomplete utterance and requires a full silence interval before accepting fresh speech, so a partial command is never sent to an agent. Transcription backpressure or a closed recognizer cancels only that utterance; microphone consent remains active. Real device errors and default-device changes still stop capture explicitly. The microphone button mutes instead of pausing: the audio run stops feeding capture (`AudioController::set_listening`), an utterance still being spoken is dropped, the current reply keeps generating and playing, and the device closes once playback is idle. Global pause and Stop still cancel the reply. Headphone and playback-only sessions do not enqueue unused echo-reference frames.

`audio-events.log` in the application data directory records fixed lifecycle events, version, timestamps, character counts and internal device failures. Each reply also adds one `turn_timing` line with stage latencies in milliseconds from the end of speech (or from the start of a typed turn): transcript accepted, request ready, first token, first passage sent to TTS, first audio and text complete. In a three-way conversation the silence relay adds fixed lifecycle lines: `trio_relay_skipped` (an exchange that did not arm it, with `stopped`, `no_reply`, `off` or `cancelled`), `trio_relay_armed` (`delay_s=N`), `trio_relay_wait` (`cooldown` or `quick_silence`, before each wait for the user), `trio_relay_fired` (`first`, `silence` for a further silence step or `chained`) and `trio_relay_ended` with a reason code: `cancelled` (the relay token: speech, typing, Stop, pause, new turn), `off`, `limit`, `passes`, `widget_hidden`, `paused` (microphone muted or voice paused), `busy` (session not idle), `stale` (guest, master or session changed), `failed` (provider or turn error) or `not_armed:<condition>` (`cancelled`, `live_tag`, `response`, `transcription`, `session`, `master`, `guest`). It contains no recording, transcript, prompt, profile/device name, server address or credential. It rotates at 128 KiB to one previous file. It is diagnostic evidence, not a replayable conversation, and is excluded from publication.

Provider HTTP requests share one connection pool for the whole app, keeping connections and TLS sessions alive between turns. Streamed replies have no overall time limit below one hour; they fail only after 180 seconds without data, first token included. Context budgets use loaded capacity, reply reserve and margin. UTF-8 estimation is conservative, not an exact tokenizer count. History and secondary memories are bounded; reasoning is excluded from speech and dialogue storage.

## Lifecycles

Optional web search runs before final generation, within the same cancellable profile/generation operation. Explicit requests skip the local structured search planner; automatic mode passes only the current question to it. Each profile chooses its search access mode (off, on request or automatic); since 1.3 the engine (DuckDuckGo Lite, Brave, Tavily or a configured SearXNG server) and its key are global settings, migrated once from the previous per-profile configuration. Brave/Tavily credentials go only to fixed HTTPS endpoints; SearXNG accepts HTTPS or private-network HTTP without embedded credentials. Requests have time/size limits, no redirects and no arbitrary-page fetching. Keys use the OS vault. Evidence is included as untrusted user-role text, with whole sources bounded against the model context. Search receipts and the sources actually supplied are stored in the assistant's history row (schema 4), separate from memories and profile exports. The panel can open a source selected by profile/message/index; it cannot supply an arbitrary URL. The widget cannot invoke that command.

`ModelManager` serializes loading, resolves aliases before deletion, rejects ambiguity and preserves foreign instances. Shutdown waits for loads, stops audio, saves geometry, unloads its instance and verifies the catalog. Failure offers retry/stay/explicit exit.

`voice_startup` shares a cancellable readiness attempt (ten-minute budget; slow, 5xx or "loading" answers and a living owned process keep it `starting`, only a dead process, an exhausted budget or a definitive answer make it `error`); root cancellation prevents late launch during exit. `service_process` resolves the prepared VoiceStudio Python runtime and starts its API without Electron. Shared speech settings override legacy per-profile connection fields at runtime. Owned process groups/jobs allow ownership-based cleanup without terminating pre-existing servers: `owned_process` starts the server suspended and puts it in a `KILL_ON_JOB_CLOSE` job before it runs (Windows, no breakaway), or in its own process group killed on exit with `PR_SET_PDEATHSIG` for a crash (Linux, forked by one long-lived thread). Every quit path ends in `shutdown_services`, `RunEvent::Exit` repeats it as a safety net, and the outcome is one `voicestudio_stopped` / `voicestudio_left_running` / `voicestudio_stop_failed` line in `audio-events.log`. A server that dies has its leftover workers killed before a retry starts another. `voice_warmup` runs when `voice_startup` reaches ready (cold when the first probe was not ready), and when the active companion or the guest changes: a discarded `Providers::speech` word per (URL, engine, voice, language) and half a second of silence through `batch_transcribe`, once per VoiceStudio run, without `voice.gate` or the core lock, cancelled on pause and quit, logged as `voicestudio_warmup`. No additional Python runtime or model download manager is added. LM Studio startup is independent.

## Updates and boundaries

`updates` exposes status/check/install only to the panel. No arbitrary URL, path or process command comes from the webview. GitHub checks are manual and use the official fixed repository. The widget has no updater permissions. Signed downloads are verified before shutdown.

Installed copies use NSIS. Directly launched copies prepare a verified new executable as a temporary helper. It binds the target to the old process, verifies the signature and version, waits for clean exit, then replaces the file with a backup and restarts. User databases are not replaced.

A restrictive CSP limits the webview. Provider responses and release notes are untrusted text. Update test overrides are debug-only, loopback-only, with isolated data.

References: [capabilities](https://v2.tauri.app/security/capabilities/), [updater](https://v2.tauri.app/plugin/updater/), [WebView2 testing](https://playwright.dev/docs/webview2), [contracts](CONNECTIONS.md).

## Hermes agent mode

`hermes` is a distinct remote-agent provider. Native session SSE carries user text only: local prompt construction, web planning, memory operations, model/context management and emotional-avatar behavior are bypassed. `Snapshot.companion_capabilities` exposes `local_personality`, `local_memory` and `local_emotions`; all are false in Hermes mode. The expression renderer and stream adapter honor this contract; future generators must do so too.

The official `/api/sessions` and session-chat stream APIs own the transcript. Device-local SQLite mappings isolate each companion and profile endpoint and retain the server’s current session after compression while keeping the displayed transcript stable. `/new` rotates the mapping without deleting history or remote memory. Profile exports contain connection preferences only. Keys are scoped to the exact routed endpoint in Windows Credential Manager; technical events and tool results never enter TTS. Approval responses are tied to the active generation and only offer once/deny.

The `/stop` shortcut and widget button interrupt the owned run through `POST /v1/runs/{run_id}/stop`, then poll its status for confirmation. They never stop a server or service. A per-client async gate prevents another Hermes run from starting while cancellation is unresolved. Failed cancellation retains the run handle for retry; the UI reports uncertainty instead of claiming success.

## Conversation illustrations and desktop tools

Schema 8 added per-profile illustration/search preferences, image batches, slideshow timing and the global theme; schema 9 (1.0) adds the separate mood state; schema 10 adds message speaker attribution for three-way conversations. The legacy JSON export is version 5 (version 4 added these configurations, version 5 the positive prompt addition); versions 1–4 remain accepted. The default export is the `.sherka.zip` archive v1 described in [companion packs](COMPANION_PACKS.md). Physical descriptions are independent of personality and initially come from the shared `config/presets/appearance.json` data. Themes affect application chrome; the active avatar halo uses the profile's accent. The widget samples portrait alpha bounds and repositions controls after image loading, resizing or expression changes.

Text and image cells share the widget's transparent native window. The input is positioned below its controls; the image has a relative drag position and its own size. `widget_surface` validates/coalesces surface growth without resizing the avatar, clamps to the monitor, and saves the base avatar bounds. The widget can submit messages and control its preview, but cannot access keys or raw files. Text follows the existing conversation path, including Hermes commands. The illustration path rejects Hermes both in native code and the UI. Widget error notices expire after 2.8 seconds above the controls and never intercept pointer input.

When generation and text consumption finish successfully, `text_complete` permits scene planning while speech is still active. With illustrations enabled, the assistant row is saved provisionally and finalized with delivery receipts after playback. The illustration manager uses a separate cancellation token and the latest user/assistant pair to request structured scene JSON from that character's provider. Scene text never enters speech, history or memory. `illustration::final_prompts` composes the exact ComfyUI prompts (validated scene, authoritative negative with the companion's unwanted traits, positive addition); the manager keeps them for the latest exchange and exposes them in the illustration status. The widget can replace them with verbatim text (`set_illustration_prompt`), which skips scene planning for that same exchange, including live variants, until a new reply or `reset_illustration_prompt`. The planner first decides whether the companion belongs in the scene and how many characters it contains, then composes Illustrious tags or SDXL visual prose for the profile's selected model family. The user's visual request takes priority over the reply. Existing context bounds still apply.

**The companion knows and obeys the generator state.** Like memory and web search, the image generator follows *local intent → application action → receipt*; the model never switches anything and has no tool call. `illustration::image_intent` reads the user's words (phrases in the seven languages, negations excluded, so "image" or "imagine" alone do nothing) as `SwitchOn`, `SwitchOff` or `Make`, and `asks_switch_on` tells whether a request also asks to switch it on. In `prepare_turn`, before the web and memory steps of a normal user turn, `switch_images` builds the facts (enabled, `generator_ready`, trio, waiting request) and `image_control::plan` returns the decision: an optional switch, what the companion is told (state with a receipt, only a reason, or nothing) and what happens to the waiting request. The switch is the widget button's `desktop_tools::set_image_enabled`: it only saves the profile, synchronizes the illustrations (their own token) and notifies the interface, so it neither cancels the turn nor takes `voice.gate`. A failed switch becomes the `SwitchFailed` receipt. The decision becomes an `ImagePrompt` passed to `prepare_context_with_avatar`: a state line (on/off, model family and checkpoint short name; on: the application illustrates the exchange after the reply, the model cannot see the picture; off: it cannot switch it on and must not promise an image) and a receipt (`SwitchedOn`, `SwitchedOnWithRequest`, `SwitchedOff`, `Preparing`, `NeedsSwitchOn`, `Unavailable`). Without a set-up model (no checkpoint and no custom workflow), Hermes, idle invitations and the second speaker of a trio the companion is told nothing; in a trio only a request gets the `ThreeWay` receipt and the switch is never touched. The receipt is also stored in `LiveConversation::image_receipt`: after the reply `image_control::illustrate_after_reply` skips the command exchanges (`SwitchedOn`, `SwitchedOff`, `NeedsSwitchOn`, `Unavailable`), while `Preparing` and `SwitchedOnWithRequest` illustrate normally. The planner already reads the user's sentence verbatim as the latest message, so a request such as "make me a cat astronaut" drives the scene in the model family's format.

A request made while the generator is off (`NeedsSwitchOn`) is kept as a **waiting request** in `Illustrations` (memory only: companion, session and the user's text, at most 2400 characters). Any user turn that is neither a switch-on nor a request (a switch-off included), any idle or event turn, a companion or session change, turning the generator off and the start of drawing clear it; a switch-on keeps it and a new request replaces it. The next illustration job, whether started after "switch on the generator" or by the Image button, reads it instead of the latest user row as the scene planner's user request, with the latest companion reply as context, and uses it up only when it reaches the drawing step. An "illustrate-and-switch-on" request (`Make` with a switch-on phrase) switches the generator on first and is illustrated normally. In live mode a switch-on inside a turn also clears the resume flag so that the command exchange is not drawn when the turn releases its priority.

**A requested image starts by itself, even if ComfyUI is not running.** Switching the generator on starts ComfyUI (`comfy_startup::synchronize`); the post-reply job waits for it (`ComfyStartup::ensure`, bounded by the 5-minute startup budget) with the "planning" phase, and the image cell shows the usual ComfyUI start message meanwhile. Starting a conversation turn, a detected voice (`Illustrations::cancel(false)`), transcription, memory extraction or a spoken event cancels any job and used to lose it for good outside live mode, so a request made while ComfyUI was still starting vanished. A job cancelled by one of them *before it draws* (phase "planning") now sets the resume flag, whatever the mode, and the last released lease starts it again with the waiting request still in place. A job that is already drawing is not resumed. A context change (generator off, another companion or session, new settings), clearing the conversation and shutdown drop the flag and the waiting request. A job that finds itself stale without being cancelled returns the cell to idle instead of staying in "planning".

The widget **Image** button reuses the same switch. When it turns the generator on (not by voice, not in a trio, not for Hermes, and a model is set up) and no request is waiting, the master makes one brief spoken remark (`AppEvent::ImagesOn { family }`, master only, spoken through `speak_event`, gated by `check_event` like the arrival remark: silent unless the conversation is idle). The remark turn preempts any running illustration, so the old exchange is not illustrated in that case; when the remark cannot start, or a request is waiting, the button illustrates at once as before.

Rust discovers only required ComfyUI node classes, validates a bounded graph, replaces its prompts/model/LoRAs and uses temporary preview output. The default graph is derived from the supplied workflow. The full checkpoint catalog is available with relative folder filters; the family (Illustrious or SDXL) is chosen explicitly. Hidden Turbo selection is resolved from the server's installed catalog. Optional IP-Adapter guidance with the neutral portrait, ×1/×1.5 latent scaling between the two samplers and a final ×2 upscale are graph options; advanced mode overrides per-pass steps/CFG and the shared sampler. No models are bundled. Configuration is limited to loopback/private-network servers and replies are bounded before pixel decoding and PNG normalization.

A serialized job gate coalesces pending work. One scene plan produces 1–8 sequential image jobs with fresh seeds and partial preview updates; the UI loops them at the configured interval with decoded 500 ms crossfades. Publishing requires the same profile, session, configuration, provider, latest reply and generation sequence. New input, clearing, disabling or shutdown invalidates older results. Cancellation deletes an owned queued prompt by ID; running ComfyUI work is allowed to drain rather than interrupting another client's job. The displayed images stay in memory; ComfyUI owns any temporary server files/history.

Dropped text is staged in the input cell. Image attachment support comes from provider catalog metadata, or an explicit confirmation for undocumented models; Hermes and explicitly text-only models reject it. Native code validates up to four bounded PNG/JPEG/WebP files, decodes and normalizes them to PNG with a maximum dimension of 1024, strips metadata, and inserts OpenAI/Anthropic image blocks into the final user message only. Pixels never enter SQLite, memory extraction, scene planning or profile exports. A conservative per-image token margin supplements the text budget; it is not an exact vision-token calculation.

The image generator never starts with a companion: `Companion::open` and `switch_profile` save the newly active companion's `illustration.enabled` as false (a normal profile update, so its revision advances), before the widget, illustration manager and ComfyUI startup synchronize. The widget's image cell and the ComfyUI launcher both follow that flag, so neither opens until the Image button switches it on for the session.

Native test instances with an explicit `SHERKA_DATA_DIR` derive their singleton identifier from its absolute path. Tests therefore cannot restore a normal running user instance, while two instances using the same isolated folder still share a singleton.

## Avatar expressions

Profile schema 6 introduced six optional expression overrides in `avatar_emotions`; the existing `profile.avatar` remains neutral. The seven-state enum is closed. An explicit null override suppresses a bundled expression. The Sherka preset uses bundled asset URLs so snapshots do not copy six large images on every refresh. Bundled companion images ship as lossless WebP. Upgrading an existing Sherka with no custom portrait adopts this pack once; custom portraits remain untouched. Neutral and custom expression bytes are validated PNG/WebP, normalized and stored locally as lossless WebP, so every pixel and alpha value is kept; images stored by earlier versions stay PNG and are served with their own media type. ComfyUI uploads, vision requests and companion archives receive the same pixels re-encoded as PNG. Imports validate all images before creating a new profile and use a 48 MiB aggregate JSON limit. Export version 2 introduced the bundled preset reference and custom image overrides; version 3 added illustration preferences, version 4 search/batch preferences and version 5 the positive prompt addition. Voice remains in that same profile’s connection configuration and is edited from the avatar UI.

The bundled preset enum also includes Botsy, Alba, Kit and Minerva, each with seven images. A persisted one-time initialization flag adds missing starter profiles without restoring profiles subsequently deleted by the user. Their personality is localized at creation; model and voice choices remain unconfigured. The original built-in Sherka retains its interface-language synchronization.

Alba retains the serialized `candis` preset identifier for compatibility with existing profiles and exports; her images resolve to the new Alba pack. On startup, an unchanged shipped Candis name/personality upgrades to Alba, with only the identity word changed in the localized text. User-edited names/personality and all profile IDs, settings, images, history and memory are preserved. Minerva's bundled image URLs point to the V2 pack. No database schema change is needed.

The Companions page groups identity, avatar/voice, provider, model, speech and web-search preferences. Search mode is stored per profile; older profiles inherit the previous global preference until edited. Hermes always resolves this mode to off. Saving an unrelated profile field rebases a pending connection draft only when its persisted connection values are unchanged.

When images are available, `prepare_context_with_avatar` adds a short expression instruction inside the existing context budget. If mandatory input leaves too little room for this optional instruction, the turn stays neutral rather than failing or truncating the user’s message. A bounded `ExpressionStream` removes the leading `[[emotion:STATE]]` header across chunk boundaries before text reaches the live reply, history or `SpeechText`. Invalid or absent metadata stays neutral. No separate inference request is added. An empty marker-only reply reports an empty response. Hermes bypasses both prompting and parsing. Expression updates use the same operation tag as text and audio; completion, cancellation and profile switch reset neutral. The widget decodes a new image before a 500 ms opacity crossfade, with at most two layers and only the latest pending expression. Same-character refreshes preserve these image nodes so cancellation can fade back to neutral without resetting the animation. Switching characters discards the previous layers. Reduced-motion preferences skip the fade; hover controls and dragging stay independent.

## Persistent moods

`mood` keeps an optional, bounded per-profile reservoir in schema 9's `mood_state`, separate from messages and facts. One completed text exchange advances it once: grounded user cues and the reply's expression add capped points, repeated model signals diminish, every exchange without a trigger decays the scores and kindness can de-escalate anger. Displaying a mood never feeds back into scores or into the language-model prompt, and there is no timer or extra model call, so it cannot loop. An epoch fences in-flight replies when the user resets the mood independently or clears the whole conversation. Copies and exports carry only the `mood_persistence` switch; Hermes is excluded.

## Spontaneous conversation

`initiative` (Tauri side) keeps one timer per classic companion with the configured minimum/maximum idle minutes. The delay is drawn randomly in that range and reset by activity. A due timer waits while the user speaks, types, the widget is hidden or the conversation is paused. After one invitation it stays disarmed until a real user reply, so the companion never monologues. Hermes is excluded. In a [three-way conversation](#three-way-conversation) the master's timer also covers the guest.

## Three-way conversation

A second companion, the **guest**, can join the active companion, the **master**, for the rest of the application session. The master keeps the microphone, the text cell and all controls; the guest only speaks, listens through the same turn and has its own avatar window. Everything below is additive: with no guest, the pipeline is the solo one described above.

**Session, turn and tags.** The engine holds one optional guest id next to the active profile id. A trio turn is a single operation: `Session::begin_peer` starts the second speaker's generation under the same cancellation token and operation tag as the first, instead of replacing them as a new `begin` would. The existing VAD barge-in, Stop, pause, microphone mute and profile switch therefore cancel both speakers at once, and late events from either cannot reactivate the turn. Each text, expression and audio event also carries the speaker's profile id so the panel and the two windows apply it to the right avatar. The guest is never persisted: switching the master, restarting, or switching either companion to Hermes removes it, and the core refuses `set_guest` for a Hermes master or guest and for a companion without a configured voice.

**Sequencing.** Who answers is decided locally, and exactly one companion answers the user: the one named within the first three words of the message, otherwise a coin toss picks one (`trio::answerer`). Names are matched case- and accent-insensitively and tolerate one edit for names of at least five letters, which absorbs speech-recognition slips. The answerer cannot pass. The other companion does not answer straight away: it prepares a reaction in the background (see Pre-generation below) and reacts to the user's message and the answer after the cooldown, if the user stays silent (see Relay after silence and chat below). That reaction, and the replies that follow, may be `[[pass]]` when the companion has nothing to add; the marker is stripped like the expression header, never spoken and never stored. Companions exchange text directly; no transcription happens between them. Speech uses one playback queue and one TTS request at a time, each companion with its own VoiceStudio engine, voice, speed and volume, so voices never overlap. Only the spontaneous idle trio (timer) still has two speakers back to back: a coin picks who opens and the other reacts once, prepared during the first one's speech.

**Pre-generation.** Once the answerer's text is complete, the LLM is free, so the other companion prepares its reaction in the background while the answerer's voice is synthesized and played. Nothing is displayed, saved or stored in the live state: the reaction is buffered under a detached tag (`detached_tag`, `Gate::Detached`) that the session never accepts and that answers only to the relay token (`Companion::arm_relay`, armed as soon as the answerer is known). The language model starts once the answerer's text is complete; once the answerer's speech is synthesized, up to two first passages of the prepared reply are synthesized ahead into a phrase-to-PCM cache. This preparation does not hold the session turn open: the turn ends normally with the answerer's reply (`finish_response`), so the session is idle and the user can speak during the wait. When the cooldown elapses, the relay promotes the prepared reply: buffered tokens replay instantly and cached passages play without new TTS requests. Any user activity cancels the relay token and so drops the preparation, which is then neither spoken nor stored. If the preparation failed or does not match (its follow message must equal the real one; a phrase mismatch drops the cache), the companion generates as usual. The same mechanism with a pending peer tag (`Session::begin_pending_peer`, `accepts_pending`, `promote_pending`; cleared by cancellation) prepares the second speaker of a spontaneous exchange during the first one's speech, and the next speaker of a chain while the current one speaks. There is still one voice at a time, and one TTS request at a time. `turn_timing` marks of a promoted speaker are relative to its promoted turn, so its first-token time looks near zero.

**Relay after silence and chat.** After every user turn that ended normally in a trio (the answerer replied, not stopped or failed) and after the arrival remark (`AppEvent::arms_relay`, decided by `relay_follows`), the companions wait for the user; never after an idle invitation, a spontaneous exchange or a solo turn. `schedule_relay` hands the relay token armed before the answer to `run_relay`, which drives a small state machine, `trio::RelayState` (silences elapsed, replies produced since the user's message, passes in a row), through pure decisions: `RelayState::next(relay_seconds)` returns `Wait(cooldown)` for the first silence (`relay_seconds`: off, 3 to 30 s, default 8 s; the UI offers off/5/8/10/15), `Wait(QUICK_SILENCE)` (1 s) for the second, then `Chain(600 ms)`, and `Stop` when `relay_seconds` is 0, after `CHAIN_LIMIT` = 20 replies since the user's message, or after two passes in a row. Once the answerer has finished, the companions wait for the cooldown. If the user stays silent, the other companion (`trio::reactor`, the participant who did not produce the last spoken reply) reacts to the user's message and the answer, using the prepared reply and audio; the very first relay's follow message includes the user's message (`follow_message(Some(user), ..)`), later ones do not (`None`). The companions then leave a quick silence of 1 s and the answerer reacts to that reaction. From then on they chain with a 600 ms pause, alternating, until the user cuts in, 20 replies since the user's message, or two passes in a row. A companion that passes (`[[pass]]`) is asked again only after a further cooldown. After the arrival remark there is no user message: the plan holds the remark as the last spoken reply, the master as its author, and the first relay's follow message is just the master's line, so the guest reacts to the remark (prepared during it, then after the cooldown, then the same quick silence). Any user activity ends the relay and drops the prepared reaction (see below); the cycle then starts over with a single answer and the full cooldown. With `relay_seconds` at 0 only one companion answers and nothing follows. Relay and chained replies write no user row and schedule no memory extraction; their replies are saved and mirrored like any other.

**Chain turn, prefetch and cancellation.** A reply that another follows at once (`TrioStep::Second { continues, signals }`) leaves the session turn open (`finish_generation`), so one barge-in, Stop or pause cancels the whole chain through the session token, and the next speaker is prepared with the same pre-generation as above (pending tag, buffered tokens, `PcmCache`) while the current one speaks; `hand_over` promotes it or begins a fresh peer. A reply followed by a wait closes the turn (`finish_response`), so the session is idle while the user is expected to speak, and each later step starts a fresh turn. The relay token also outlives the chain's own turns: they use `Companion::reset_live_keeping_relay`, because `reset_live` (a user turn) cancels the relay. Neither it nor `reset_live_for_event` (idle invitation, arrival remark, second speaker of a spontaneous exchange) cancels a pending memory extraction, which only `reset_live` and `stop_response` do. The token is cancelled by any new turn, speech detection, `initiative_activity` with `typing` (typed text in a text field; a click or another key only feeds the spontaneous-conversation timer), Stop or pause (`stop_response`, `pause_voice`), removing or changing the guest and switching the master. Before every step the chain also stops if the microphone is muted or the voice paused (`initiative_paused`), the widget is hidden (`windows::widget_visible`), or the session is not idle (or, in an open chain turn, no longer the chain's). With a paid cloud provider every reaction is billed, including prepared reactions that get discarded when the user cuts in.

**Quick replies.** With the global **Favor quick replies** setting (`settings.trio`, off by default), every trio generation (first, second, relay, spontaneous) caps the reply budget at 160 tokens and the prompt asks for one or two short spoken sentences without lists, so speech starts sooner and exchanges flow.

**Arrival remark.** When the user adds a guest, the master receives an application event: the guest's name and, unless the master already knows that companion (its history already contains lines from it), a short description (the guest's personality, cut to about 500 characters). The master makes one short, in-character spoken remark about the arrival. The master speaks alone; the guest prepares its reaction during the remark (as for an answer, see Pre-generation), reacts after the cooldown (`relay_seconds`) if the user stays silent, and the 1 s quick silence applies from there before the companions chain; the remark is saved in its history and copied to the guest's, with no user row and no memory extraction, and a barge-in stops it. It does not depend on spontaneous conversation and is skipped if the master has no model or voice or the session is busy. The application-event mechanism is generic and not specific to trios.

**One model.** `Connections::with_llm_of` returns the guest's connection with the master's provider, API and LM Studio URLs, model, context limit, response budget, reasoning and vision confirmation. Only one LM Studio model stays loaded, so `ModelManager` resolves the same instance for both and performs no load or unload on invitation or removal. Personality, instructions, language, voice, expressions, memory and mood stay the guest's own. Credentials follow the borrowed provider and API scope.

**Prompt.** Each companion's system prompt gains a short paragraph naming the other companion: the conversation has three participants, lines prefixed `Name:` come from the other companion, the reader speaks only for itself in the first person and keeps replies short. When history holds lines from a companion who is no longer present (the guest was removed, or a previous guest while a new one is present), the prompt adds that those name-prefixed lines came from another companion who took part earlier, has left and can no longer hear. The second speaker is also told to react without repeating the first reply or to answer `[[pass]]`. The other companion's lines are inserted as user-role messages prefixed with its name. So that the user is never mistaken for the other companion once same-role messages are merged, whenever the prompt is multi-party (a peer is present, or the history holds a line with a `speaker`, including departed companions only) every line of the user carries a label, the user's history rows and the final message alike: `User: ` by default, or the optional **Your first name** (`settings.trio.user_name`, at most 40 characters, no colon or control character, empty = no name) as `Arthur: `. The peer paragraph names the three participants (the user, the reader, the other companion), says which prefix belongs to whom and forbids attributing one's words to another; the departed-companion note says how the user's lines start when no peer paragraph does. The second speaker's follow message carries the label itself (`follow_message(user, user_name, ..)`); the final message of `prepare_context_with_avatar` is labelled only for `Last::User`, never for `Last::Attributed` (follow messages and application events, which already say they are not a user message). Web evidence is never labelled. A plain solo prompt, without any speaker in the history, is unchanged. Because that produces consecutive user messages, same-role messages are merged for every provider (the Anthropic adapter already did), as some local chat templates require alternating roles. Web evidence is merged into the final user message. Attached images reach only the first speaker.

**Storage.** Schema 10 adds nullable `speaker_id` and `speaker_name` to `messages`; NULL means the user or the database's own companion. The user's message is written to both databases. A reply is saved in its speaker's database and copied, attributed, into the other's, so each companion keeps the whole three-way thread and re-inviting the same guest resumes it with context, even after a restart. An interrupted reply is saved as interrupted in the speaker's database, and only the heard part is copied to the other. Memory extraction reads only user rows, so a companion never memorizes the other's words as the user's; both companions can learn facts about the user. A per-master list of the last three guests lives in settings and feeds the picker's **Recent** section. Exports and companion archives still exclude history. As with earlier schema changes, downgrading after the migration is not supported.

**Memory, web and moods.** Explicit memory commands and web search are handled by the answerer (the first speaker of a spontaneous exchange), so naming a companion directs them to it. The reacting companion (prepared reaction, relay, chain) uses its own memory recall and history, with no memory plan or web search. Automatic extraction runs for both companions one after the other: `schedule_memory` waits 30 s after the user's turn, and only a turn of the user (which schedules its own), Stop or pause, clearing the conversation or a master or guest change cancels it. The relay's reactions, chained replies, the arrival remark and idle invitations do not; and if the companions are still talking when the delay elapses (`live.tag` set by a relay or chain step), the extraction waits for the session to be idle instead of aborting, polling every second for at most five minutes (`when_quiet`, cancellable by the job's token), and again before applying its result. Each companion advances its own persistent mood with its own epoch fence, and the reply expression is shown only on the window of the companion currently speaking. Privacy and maintenance commands (clearing the conversation, memory optimization and their confirmations) apply to the master only.

**Spontaneous conversation.** When the master's initiative timer fires with a guest present, a coin toss picks who opens and the other reacts once. The timer then stays disarmed until the user replies, as in solo.

**Guest window.** The guest is shown in a separate on-demand webview, `guest`, with its own minimal capability: portrait with seven expressions and 500 ms crossfades, name and speaking halo, no access to keys, files or the updater. It is a transparent window with the widget's drag and resize behaviour and size limits. Its geometry is saved per companion in `desktop_layouts`, and it hides and shows with the widget. Its name chip, remove button and resize handle are placed around the portrait's visible pixels, as the widget's controls are. The window is created when a guest is invited and destroyed when it is removed.

**Exclusions.** Hermes cannot be master or guest. ComfyUI conversation illustrations are disabled for the whole trio, in native code and in the UI. A companion without a voice cannot be invited. These limits are enforced in the core, not only by hiding or disabling controls.

Known risks: small models may write the other companion's lines or overuse `[[pass]]`; the guest paragraph can be tuned.

## Shared services and desktop geometry

VoiceStudio connection/transcription settings and the VoiceStudio/ComfyUI startup paths are device settings shared by all companions and excluded from exports; voice engine, voice and delivery remain per companion. `voice_startup` and `comfy_startup` start a local service only for loopback addresses and only when its **Start with Sherka** option is enabled. `owned_process` tracks processes Sherka launched (Windows job objects, Unix process groups); exit closes only those, leaving pre-existing and remote servers running. Avatar and image-cell geometry are saved per companion, and overlapping illustrations render behind the avatar.

`image_viewer` opens a separate full-screen window for the current illustration on the companion's monitor. The widget stays in front with its native drag/resize behavior; Esc, a second double-click, switching companions or hiding the widget restores the cell. Since 1.2, activity notifications run off the UI thread and native visibility/geometry reads complete before engine locks are acquired, which removed a desktop freeze.

## Character creation

`character_studio` (core and Tauri) drives the **Character creation** page. A connected classic companion's provider proposes an editable sheet (personality, appearance, image prompts) from the user's idea, without reading any conversation or memory. Rendering uses three fixed API workflows in `config/workflows/`: `character-neutral.json` (SDXL or Illustrious front-facing head/bust portrait on uniform dark gray, 1024 output), `character-mood.json` (Flux Klein 4B reference-latent editing for the six emotions) and `character-transparency.json` (RMBG-2.0 background removal, no user settings). Only model, text encoder and VAE selections are exposed; sampling stays as supplied. No IP-Adapter or Turbo is used for creation.

A user picture can replace the generated neutral portrait: `imported_portrait` decodes PNG/JPEG/WebP under 10 MiB with dimension limits, fits it within 1024 pixels and flattens alpha onto the portrait gray. With an image, the sheet request accepts an empty idea; the picture is attached to the structured request only when the source model reports vision support (`structured_with_images`), and other auxiliary requests never carry images. An imported neutral portrait (`neutral_imported`) is independent of the sheet and checkpoint, so only Klein model or emotion changes invalidate later stages. `Draft.prompt_overrides` holds final prompts edited per image; `studio_workflows::prompts` sends them verbatim (bounded by `illustration::exact_prompts`) and they take part in the portrait/emotion invalidation checks.

`edit_character_images` loads an existing companion (stored or bundled images through the asset resolver) with `Draft::for_existing`: its portrait becomes an approved imported neutral, images with usable alpha are reused as transparent results, and `target_profile` makes finishing write the seven images back with `set_emotion_avatar` instead of creating a profile. Raw and transparent images are tracked separately. Regenerating the neutral portrait invalidates every dependent image; retrying one emotion invalidates only its own alpha; a model change invalidates the affected stage. Publishing requires seven valid transparent PNGs and creates a new profile with empty history and memory and no inherited voice. Drafts live in memory for the application session. Creation shares conversation priority and cancellation tokens and never interrupts the ComfyUI server globally.
